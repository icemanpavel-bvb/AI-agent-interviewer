## D-010 · Уточнение не подсказывает ответ и обращается на «вы» · ✅ · 13.11.2026

**Проблема.** На тесте с GigaChat уточнение к вопросу про TF-IDF звучало как «Упомянуто ли в ответе произведение TF и IDF…»: модель пересказала формулировку пункта проверки. Это и подсказка (студент узнаёт ответ из вопроса), и обращение в третьем лице.

**Решение.** Промпт `followup.v4.md`:
- обращение к человеку напрямую, на «вы»; запрет на «Упомянуто ли / Указано ли…»;
- правила зависят от режима (`MODE_RULES` в `followup.py`): в проверке знаний нельзя называть недостающий факт, термин или формулу — спрашиваем, как человек понимает аспект темы; в собеседовании можно прямо назвать, о чём рассказать (сроки, роль, результат);
- примеры «плохо / хорошо» прямо в промпте — маленькой модели они помогают больше, чем абстрактные правила.

Код страхует: реплика в третьем лице (регулярка `_THIRD_PERSON`) отбрасывается, кандидат видит нейтральную заготовку.

**Что проверить:** на бенчмарке — долю заготовок вместо уточнений модели; если больше ~20 %, смягчать правила или добавлять примеры.

## D-009 · Исправления по первому тесту с GigaChat в браузере · ✅ · 13.11.2026

**Что увидели** (вставленный длинный ответ от другой нейросети на Q01 «задачи NLP»):
- все 4 пункта ✗, хотя задачи понимания и генерации в ответе явно были;
- анализ 48,5 с, уточнение 24,1 с; уточнение — безликая запасная фраза;
- на «что именно надо раскрыть?» агент перешёл к следующему вопросу;
- ответ молча обрезан до 2000 символов, хотя поле ввода принимало 4000;
- после правки кода `uvicorn --reload` перезапустился и сессия пропала.

**Причины и решения:**
- **Цитаты.** Модель «цитирует» формулировку пункта вместо ответа; строгая проверка сбрасывала верные пункты. Теперь `quote_match`: `exact` (дословно) или `fuzzy` (не меньше половины значимых слов, минимум 2, есть в ответе) — тогда в протокол идёт дословный фрагмент ответа. Выдуманные цитаты по-прежнему отклоняются. Порог проверен на этом случае, уточнить на бенчмарке.
- **Отладка** показывает вердикт модели до проверки и что сделал код (`model_status`, `model_quote`, `quote_check`) — видно, кто ошибся.
- **Промпт анализа v3:** цитата — строго из `<answer>`, не из пунктов; длинный ответ с разметкой читать целиком; новый `intent: clarify`.
- **Пояснение вопроса** (`clarify`) — агент поясняет, не тратя лимит уточнений и не переходя дальше; не больше 2 на вопрос.
- **Уточнение v3** получает только начало ответа (400 символов), а не весь: должно ускорить шаг с ~24 с до нескольких секунд. Проверка «не подсказывает ли эталон» не считает подсказкой слова самого вопроса. Запасная фраза в собеседовании называет темы, в проверке знаний — без подсказок.
- **Лимит 3000 символов** везде одинаковый: поле ввода (счётчик, отправка блокируется), API (422), обрезка в CLI с сообщением. В модель — не больше 5000 символов ответов на вопрос.
- **Демо-сессии сохраняются на диск** (`storage/demo_sessions/`) и переживают перезапуск сервера; если сессия всё же пропала — кнопка «Начать заново».

**Время анализа длинного ответа** (~50 с на CPU) — плата за ~1200 новых токенов промпта; для обычных ответов своими словами должно быть заметно быстрее. Проверить на бенчмарке.

## D-008 · Веб-демо до базы данных: сессии в памяти · ✅ · 12.11.2026

**Решение.** Сделать браузерную версию сразу, не дожидаясь БД (этап 1): FastAPI отдаёт API демо и чата поверх того же `InterviewRunner`, сессии хранятся в памяти процесса (`interview/store.py`), интерфейс — React (`/demo`, `/i/:token`).

**Почему.** Тестировать и показывать в терминале неудобно. Контракт API чата (`/interview/{token}/...`) уже тот, что в архитектуре: на этапе 2 хранилище заменится PostgreSQL, а фронтенд менять не придётся.

**Ограничения:** сессии пропадают при перезапуске сервера; не больше 200 сессий, удаляются через 6 часов без активности; работает только при `DEMO_MODE=true`.

**Попутно:**
- недоступность модели (`LLMUnavailable`) больше не маскируется под «ответ засчитан»: API отвечает 503, ход не засчитывается, ответ можно отправить ещё раз;
- лимит длины ответа модели поднят до 400 токенов: JSON с цитатами по 5–6 пунктам не помещался в 200–300;
- настройки читают `.env` из корня репозитория и не падают на незнакомых ключах.

## D-006 · Банк вопросов для проверки знаний · ✅ · 12.11.2026

**Решение.** Для сценариев типа `knowledge_check` вопросы хранятся **банком** (до 60), а на одну сессию выбирается выборка (`session.size`, по умолчанию 10, максимум 20):
- `balanced_random` — сначала по одному вопросу из каждой темы, остальные случайно; порядок в сессии — как в сценарии;
- режим **тренировки по теме** (`allow_topic_choice`) — все вопросы одной темы подряд;
- выбранные вопросы сохраняются в `interview_session.question_plan`, поэтому при возврате по ссылке план не меняется.

**Для собеседований ничего не меняется:** не больше 10 вопросов, все задаются по порядку (требование БТ). Схема это проверяет.

**Почему.** Сценарий по лекциям нужен и для подготовки к экзамену: каждый новый заход даёт другие вопросы, а охват всех тем сохраняется. Длина одной сессии остаётся разумной (~15–20 минут).

**Сценарий студента расширен:** 8 тем, 25 вопросов, добавлены BOW и TF-IDF (Q02–Q04) и задачи NLP и аудио (Q01). Эталоны по BOW и TF-IDF — по общепринятым определениям, слайдов в файле нет; пометка в `recruiter_only` у вопросов.

## D-005 · Четыре сценария и демо-страница · ✅ · 12.11.2026

**Решение.** В системе четыре сценария (файлы в `scenarios/`, описание — `scenarios/README.md`):

| Сценарий | Тип | Статус |
|---|---|---|
| Аналитик ОМТО (гайд T06) | собеседование | готов |
| ML-инженер Junior — **основной** | собеседование | готов |
| ML-инженер Middle | собеседование | черновик |
| Проверка знаний по лекциям NLP | проверка знаний | черновик, банк из 25 вопросов по 8 темам (D-006) |

- **Уровень основной вакансии — Junior** («для начала самое то»). Учебные и пет-проекты считаются опытом; в Q00 нет порога стажа, вместо него пометка «нет ни одного проекта».
- **Тип сценария** `kind`: `job_interview` (собеседование) или `knowledge_check` (проверка знаний). Агент работает одинаково; в протоколе для проверки знаний — «тема раскрыта / частично / не раскрыта». Баллов нет.
- **Кто выбирает сценарий.** В реальной работе — рекрутер («Создать вакансию из шаблона»), ссылка кандидата привязана к вакансии. Для тестов и защиты — **страница `/demo`**: тестировщик сам выбирает сценарий и сразу проходит интервью. Включается `DEMO_MODE=true`; демо-заявки помечаются и удаляются через 7 дней.
- **Порядок:** схема → ОМТО → ML Junior → студент (по лекциям) → ML Middle.

**Почему.** Один агент на четырёх разных сценариях — наглядное доказательство универсальности на защите. Сценарий «для студента» удобен для бенчмарка: правильные ответы известны из лекций.

**Осталось:** материалы лекций для сценария студента; ревью эталонов ML Middle.

## D-001 · Локальная модель: GigaChat 3.1 Lightning · ✅ для разработки · 10.11.2026

**Решение.** Для разработки и демо на ноутбуке используем **GigaChat 3.1 Lightning** (`ai-sage/GigaChat3.1-10B-A1.8B-GGUF:Q4_K_M`, 6,5 ГБ) через Ollama. В Ollama модель называется `gigachat-lightning`.

**Почему:**
- Железо разработки — ноутбук без отдельной видеокарты: Intel i5-13420H, 16 ГБ RAM. Модель работает на CPU.
- Архитектура MoE: 10B параметров всего, но при генерации активны только 1,8B. Поэтому на CPU она по скорости близка к маленьким моделям, а русский, по данным Сбера, лучше, чем у Qwen3-4B.
- Лицензия MIT, работает локально (152-ФЗ, бюджет 0 ₽).
- 8B-модели (T-lite 2.1, Qwen3.5-9B) на этом CPU генерируют примерно 5–7 токенов/с, для чата это медленно.

**Замеры на ноутбуке (10.11.2026):**

| Сценарий | Чтение промпта | Генерация | Итого |
|---|---|---|---|
| Свободный чат, холодный старт | 1102 ток., 33 ток/с, 33 с | 213 ток., 12,8 ток/с | 50 с |
| Анализ ответа (JSON по схеме), 1-й запуск | — | — | 5,9 с |
| Анализ ответа (JSON по схеме), повтор | 1159 ток., **из кэша, 0,15 с** | 36 ток., 2,8 с | **3,0 с** |

Тестовый ответ «работал немного, писал запросы» модель верно определила как `partial` и назвала оба недостающих пункта.

**Что выяснили про модель:**
- Официальный шаблон чата сам вставляет в начало каждого запроса служебный блок `DEVSYSTEM` (~1000 токенов). Блок одинаковый, поэтому после первого запроса берётся из кэша. Шаблон **не меняем**: модель обучена с ним.
- Кэш работает, только пока модель в памяти, поэтому нужен `OLLAMA_KEEP_ALIVE=30m`.
- При росте контекста скорость падает: при 2000 токенах чтение промпта 33 → 17 ток/с, генерация 12,7 → 9 ток/с.
- Модель склонна уверенно выдумывать (выдумала «gigachat-13b-llama2») и один раз перепутала роли в свободном чате. Поэтому обязательны `temperature: 0`, JSON-схема и проверка цитат кодом.

**Правила, которые из этого следуют:**
1. Каждый вызов модели — короткий отдельный запрос без растущей истории диалога.
2. В начале промпта — неизменная часть (системный промпт, вакансия, вопрос, пункты проверки), в конце — ответ кандидата. Тогда начало берётся из кэша.
3. Ответ модели всегда по JSON-схеме (`format` в Ollama), `num_predict` около 200.
4. При старте бэкенда — «прогревочный» запрос, чтобы первый кандидат не ждал ~30 с.
5. Ollama запускается в системе, а не в Docker-контейнере, с `OLLAMA_KEEP_ALIVE=30m` и `OLLAMA_NUM_PARALLEL=1`.
6. В памяти одна модель: и интервью, и протокол делает одна модель (на 16 ГБ две не поместятся).

**Запасные варианты:** GigaChat API через тот же LLM Gateway; T-lite-it-2.1 или Qwen3.5-9B, если появится сервер с видеокартой.

**Осталось:** бенчмарк на 15–20 размеченных ответах (этап 0.3), чтобы проверить стабильность, а не один пример.

## D-003 · Хранение сценариев и ответов · 🟡 предварительно · 10.11.2026

**Решение:**
- **Сценарии вакансий — JSON-файлы в репозитории** (`scenarios/*.json`): вопросы, критерии, пункты проверки, эталоны. Проверяются Pydantic-схемой и загружаются в PostgreSQL скриптом. Рекрутер правит вопросы в интерфейсе, система работает с БД.

## D-004 · Сравнение с эталоном: по пунктам проверки, а не целиком · 🟡 предварительно · 10.11.2026

**Решение.** Эталонный ответ раскладывается на **пункты проверки** (`probes`; в гайде T06 это «Уточнения»). Модель по каждому пункту отвечает: `covered` / `partial` / `missing` + дословная цитата. Эталонный ответ остаётся примером для модели, а не образцом для сравнения на похожесть.

**Почему не сравнивать с эталоном целиком:**
- правильный ответ другими словами и на другом примере выглядел бы «непохожим»;
- «насколько похоже на эталон» — это уже балл, а баллы агент не ставит;
- маленькой модели надёжнее решать короткие вопросы «есть ли это в тексте».

**Что делает код (не модель):**
- проверяет, что каждая цитата действительно есть в ответе кандидата; если нет — пункт становится `missing`;
- считает полноту: все пункты `covered` → ответ полный, иначе неполный;
- строит уточнение по недостающим пунктам (одно уточнение может спросить о двух пунктах, поэтому лимит 2 уточнения не мешает);
- для критериев с `requires_practice: true` (C01, C02 в ОМТО) всегда ставит `unknown`: по гайду самоотчёт не закрывает must-have;
- стаж по Q00 считает по периодам без двойного счёта параллельных работ; модель только извлекает даты.

**Протокол строится по критериям, а не по вопросам:** ответ на один вопрос может подтверждать несколько критериев.
