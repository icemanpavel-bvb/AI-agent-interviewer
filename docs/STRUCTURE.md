# Структура файлов проекта

> TEAM-12 · AI-ассистент первичного интервью · 08.11.2026
> Связанные документы: `docs/ARCHITECTURE.md` (как устроено), `docs/NEXT_STEPS.md` (что делать дальше).

> **Это карта всех файлов, включая будущие.** Многие файлы пока заготовки: в них только описание (docstring), кода нет.
> Что уже работает, а что нет, и как устроен рабочий код — в [`DEVELOPER_GUIDE.md`](DEVELOPER_GUIDE.md).

**Обозначения:**
- без пометки — файл уже есть в репозитории (пока заготовка с описанием);
- `🆕` — файл появится по плану, в скобках этап из `NEXT_STEPS.md`;
- `★` — ключевые файлы AI-части, с них стоит начинать знакомство с кодом.

## 2. Корень проекта

| Файл | За что отвечает |
|---|---|
| `README.md` | Точка входа для нового участника: назначение проекта, краткая структура, команды запуска и тестов. |
| `docker-compose.yml` | Описывает сервисы: `db` (PostgreSQL), `backend`, `frontend` (nginx). Ollama с моделью работает в системе, а не в контейнере (D-001); backend обращается к ней через `host.docker.internal`. Позже добавится `mailhog` для тестовых писем. |
| `.env.example` | Список всех настроек с примерами: подключение к БД, секрет JWT, провайдер и модель LLM, лимиты интервью, SMTP. Реальный `.env` с паролями в git не попадает. |
| `.gitignore` | Исключает из git виртуальные окружения, `node_modules`, `.env`, сгенерированные PDF (`storage/`), кэши. |
| `.pre-commit-config.yaml` 🆕 | Перед каждым коммитом запускает `ruff` и блокирует случайный коммит секретов. |
| `.github/workflows/ci.yml` 🆕 | GitHub Actions: линтер и тесты бэкенда, сборка фронтенда. PR не сливается, пока проверки не пройдут. |

```

├── migrations/                   # миграции схемы БД

│   ├── cli/                      # консольный прототип: python -m app.cli
│   ├── scenarios.py              # загрузка scenarios/*.json
│   ├── core/                     # общая инфраструктура
│   ├── db/                       # подключение к БД
│   ├── models/                   # таблицы БД
│   ├── schemas/                  # форматы данных API
│   ├── api/                      # HTTP-эндпоинты
│   ├── services/                 # логика рекрутера (без AI)
│   ├── interview/          ★     # ядро AI-ассистента

│   └── jobs/                     # фоновые задачи по расписанию
```

### 4.1. Корень `backend/`

| Файл | За что отвечает |
|---|---|
| `pyproject.toml` | Зависимости (FastAPI, SQLAlchemy, httpx, WeasyPrint…), dev-зависимости (pytest, ruff, mypy) и настройки линтера. Установка: `pip install -e .[dev]`. |
| `Dockerfile` | Образ Python 3.11 с системными библиотеками для WeasyPrint; запускает `uvicorn`. |
| `alembic.ini` | Где лежат миграции и как подключиться к БД. |
| `migrations/README.md` | Как создать и применить миграцию. |
| `migrations/versions/` | Файлы миграций (генерируются `alembic revision --autogenerate`). Первая появится на этапе 1.1. |

### 4.2. `app/main.py` и `app/core/`

| Файл | За что отвечает |
|---|---|
| `app/main.py` | Создаёт приложение FastAPI, подключает роутеры `/api/v1`, запускает и останавливает планировщик задач. |
| `core/config.py` | Класс `Settings`: читает все настройки из `.env` в одном месте. Остальной код берёт настройки только отсюда. |
| `core/security.py` | Генерация токена ссылки кандидата (в БД хранится только хэш), хэширование паролей, выдача и проверка JWT рекрутера. |
| `core/logging.py` | Формат логов. Правило: в логи не пишутся ПДн и тексты ответов кандидатов. |

### 4.3. `app/db/`

| Файл | За что отвечает |
|---|---|
| `db/session.py` | Подключение к PostgreSQL (async engine), фабрика сессий, зависимость `get_db` для эндпоинтов. |
| `db/base.py` | Базовый класс моделей и общие поля: `id`, `created_at`, `updated_at`. |

### 4.4. `app/models/` — таблицы БД (по схеме `06_er`)

| Файл | Таблица и назначение |
|---|---|
| `enums.py` | Все перечисления: статусы заявки и сессии, роли и типы сообщений, действия рекрутера. Единый источник названий статусов. |
| `recruiter.py` | `recruiter` — учётная запись рекрутера. |
| `vacancy.py` | `vacancy` — вакансия; `description` используется для ответов на вопросы кандидата. |
| `question.py` | `question` — базовый вопрос сценария: порядок, текст, эталон, критерии, лимит уточнений, обязательность. |
| `candidate.py` | `candidate` — ПДн кандидата (ФИО, контакты, резюме). |
| `application.py` | `application` — участие кандидата в отборе по конкретной вакансии: статус, дата «отложен до». |
| `interview_session.py` | `interview_session` — сессия чата: хэш токена, срок действия, согласие, текущий вопрос, использованные уточнения. |
| `message.py` | `message` — каждая реплика диалога с привязкой к базовому вопросу. Отсюда берутся цитаты для протокола. |
| `report.py` | `report_version` — версии протокола: v1 создаёт AI и она не меняется, v2+ — правки рекрутера. |
| `decision.py` | `decision` — решение рекрутера (пригласить / отклонить / отложить) с комментарием. |
| `audit.py` | `audit_event` — журнал действий: смены статусов, открытие отчёта, правки. По нему считается KPI. |
| `llm_call.py` | `llm_call` — журнал обращений к модели без ПДн: цель, модель, версия промпта, время, валиден ли JSON. |
| `answer_analysis.py` 🆕 | `answer_analysis` — результат проверки ответа: статусы пунктов, проверенные цитаты, полнота, решение policy (D-003). |

### 4.5. `app/schemas/` — форматы запросов и ответов (Pydantic)

| Файл | За что отвечает |
|---|---|
| `vacancy.py` | Создание и редактирование вакансии и вопросов; проверка «не больше 10 вопросов, не больше 2 уточнений». |
| `scenario.py` | Схема JSON-файла сценария: критерии (`weight`, `must_have`, `requires_practice`, `recruiter_only`), вопросы с пунктами проверки `probes`; метод `llm_view()` отдаёт сценарий без `recruiter_only` для промптов. |
| `interview.py` | Данные чата: состояние сессии, сообщение кандидата, ответ ассистента с прогрессом «i из N». |
| `application.py` | Заявка, список кандидатов с фильтрами, тело решения рекрутера. |
| `report.py` | Формат протокола (`ReportContent`, `ReportItem`, `Evidence`). Полей для баллов нет намеренно. |

### 4.6. `app/api/` — HTTP-эндпоинты

| Файл | За что отвечает |
|---|---|
| `api/deps.py` | Общие зависимости: сессия БД, текущий рекрутер по JWT, сессия интервью по токену из ссылки. |
| `api/v1/__init__.py` | Собирает все роутеры под префиксом `/api/v1`. |
| `api/v1/auth.py` | `POST /auth/login` — вход рекрутера. |
| `api/v1/vacancies.py` | Вакансии и вопросы сценария: создать, изменить, удалить, переставить. |
| `api/v1/applications.py` | Кандидаты: добавить, список, направить на AI-скрининг (получить ссылку), отказ по резюме, решение. |
| `api/v1/reports.py` | Отчёт: получить, сохранить правку (новая версия), скачать PDF. |
| `api/v1/demo.py` | Демо-режим (D-005, D-008): статус модели, список сценариев, старт сессии. Работает только при `DEMO_MODE=true`. |
| `api/v1/interview.py` | Чат кандидата: состояние сессии, согласие, отправка сообщения. Единственная часть API без логина, доступ по токену. |

Эндпоинты только принимают запрос, проверяют данные и вызывают сервис. Логики в них нет.

### 4.7. `app/services/` — логика рекрутера (без AI)

| Файл | За что отвечает |
|---|---|
| `vacancy_service.py` | Работа со сценарием, лимит 10 вопросов, запрет менять сценарий во время активных интервью. |
| `invitation_service.py` | Создание ссылки и сессии, срок действия, деактивация после завершения. |
| `application_service.py` | Таблица разрешённых переходов статусов (`ALLOWED`) и `check_transition()`. Любая смена статуса идёт только через неё и пишется в аудит. Решения рекрутера, «отложить на N дней». |

### 4.8. `app/interview/` ★ — ядро AI-ассистента

| Файл | За что отвечает |
|---|---|
| `engine.py` ★ | Главный класс `InterviewEngine`: обрабатывает каждый ход кандидата по схеме `02_interview_fsm`. Загружает сессию с блокировкой, вызывает проверки, анализ и policy, сохраняет реплики, по завершении запускает построение отчёта. |
| `policy.py` ★ | Правила диалога в коде: уточнить, следующий вопрос или завершить. Именно здесь соблюдается лимит 2 уточнений. Модель на это решение не влияет. |
| `analyzer.py` | Вызов LLM: что написал кандидат (ответ / вопрос о вакансии / не по теме / хочет остановиться) и статус каждого пункта проверки с цитатой. Сверку цитат и подсчёт полноты делает код (D-004). |
| `followup.py` | Вызов LLM: короткий вежливый уточняющий вопрос по тому, чего не хватило в ответе. |
| `candidate_qa.py` | Вызов LLM: ответ на вопрос кандидата только по описанию вакансии; если ответа там нет — «уточните у рекрутера». |
| `guardrails.py` | Проверка входа (длина, флуд, попытки взлома промпта) и выхода модели (тон, нет оценок, не раскрыт эталон). |
| `runner.py` ★ | `InterviewRunner` — одна сессия интервью в памяти: вопросы, анализ, уточнения, «не знаю», уход от темы, стоп. Используется консольным прототипом, позже — API с сохранением в БД. |
| `store.py` | Сессии интервью в памяти процесса для демо (D-008); заменится БД на этапе 2. |
| `question_plan.py` | Какие вопросы задать в сессии (D-006): собеседование — все по порядку; проверка знаний — выборка из банка с охватом всех тем или тренировка по одной теме. |
| `messages.py` | Фиксированные тексты без LLM: приветствие, согласие (с номером версии), переходы, прощание. |
| `prompts/analyze_answer.v2.md` | Промпт анализа по пунктам проверки (D-004): intent + статус и цитата по каждому пункту. Используется сейчас. |
| `prompts/followup.v2.md` | Промпт уточнения без подсказок ответа. Используется сейчас. |
| `prompts/system.v1.md` | Системный промпт: роль ассистента и запреты (не оценивать, не раскрывать эталон, текст кандидата — это данные). |
| `prompts/analyze_answer.v1.md` | Промпт анализа ответа, возвращает JSON. |
| `prompts/followup.v1.md` | Промпт генерации уточнения. |
| `prompts/candidate_qa.v1.md` | Промпт ответа на вопрос кандидата. |

Промпты версионируются в имени файла: улучшенная версия сохраняется как `*.v2.md`, старая остаётся для сравнения в eval.

### 4.9. `app/llm/` ★ — работа с моделью

| Файл | За что отвечает |
|---|---|
| `base.py` ★ | Интерфейс `LLMProvider`, функция `complete_json()` (вызов, разбор JSON, проверка схемы, повтор при ошибке, запись в журнал) и `get_provider()` (выбор провайдера по `.env`). |
| `ollama.py` | Провайдер по умолчанию: локальная модель через Ollama (только стандартная библиотека), прогрев `warmup()`. |

| `pii.py` | Замена ФИО, телефонов и email на метки перед отправкой во внешний сервис и обратная подстановка. Для локальной модели не нужен. |
| `prompts.py` | Загрузка промпта из `.md`-файла по имени и версии с подстановкой параметров. |
| `openai_compat.py` | Облачные модели через OpenAI-совместимый API и GigaChat API (D-013). |
| `registry.py` | Список моделей: локальная + облачные из `llm_keys.json`; выдаёт провайдер по имени. |
| `fake.py` | Фейковая модель для тестов: отдаёт заранее заданные ответы по очереди. |

### 4.10. `app/reporting/` ★ — протокол

| Файл | За что отвечает |
|---|---|
| `builder.py` ★ | Строит протокол по схеме `05_report_pipeline`: по каждому вопросу собирает реплики, вызывает модель, проверяет, повторяет при ошибке, сохраняет версию v1, запускает PDF и уведомление. |
| `validators.py` ★ | Проверки кодом: цитата действительно есть в сообщениях кандидата; нет баллов и оценочных слов. Используются и в отчёте, и в guardrails. |
| `protocol.py` | Протокол сессии из проверенных результатов анализа, без модели: пункты с цитатами по вопросам, сводка по критериям (темам), статистика вызовов модели. |
| `pdf.py` | Превращает последнюю версию отчёта в PDF (HTML-шаблон → WeasyPrint). |
| `templates/report.html` | Вёрстка PDF-протокола. |
| `prompts/report_item.v1.md` | Промпт: краткое резюме ответа и статус по каждому критерию с дословными цитатами. |
